# 성능 개선 기록

RAG 파이프라인 성능(지연시간/검색 품질) 개선 작업을 시간순으로 기록한다. Phase별 기능 설계는
`CLAUDE.md`에 남기고, 이 문서는 "기능은 그대로인데 더 빠르게/더 정확하게 만든" 순수 성능 개선만 모은다.

## 2026-09-10: BM25/kNN 검색 병렬 실행

**무엇을 바꿨나** (`HybridSearchService.search()`)

기존에는 아래 세 번의 네트워크 왕복이 전부 순차로 실행됐다.

```
질의 임베딩(Gemini) → BM25 검색(ES) → kNN 검색(ES)
```

BM25 검색은 질의 임베딩과 아무 의존관계가 없다(텍스트 매치라 벡터가 필요 없음). 따라서
"BM25 검색"과 "질의 임베딩 → kNN 검색"을 `CompletableFuture`로 동시에 실행하도록 바꿨다.

```
BM25 검색(ES)              ─┐
질의 임베딩(Gemini) → kNN 검색(ES) ─┴→ RRF 융합
```

- 두 작업 모두 블로킹 I/O(ES/Gemini API 호출)라, 요청마다 스레드를 새로 띄워도 비용이 거의 없는
  가상 스레드(`Executors.newVirtualThreadPerTaskExecutor()`, Java 25)로 실행했다. 이 실행기는
  `HybridSearchService` 안에서만 쓰는 로컬 스레드풀이라 애플리케이션 전역 스레드 모델(Tomcat 등)에는
  영향을 주지 않는다.
- `CompletableFuture.join()`은 예외를 `CompletionException`으로 감싸는데, 그대로 두면
  `runSearch()`가 던지는 `IllegalStateException`을 `GlobalExceptionHandler`가 더 이상 인식하지 못해
  메시지 없는 500으로 뭉개진다. `HybridSearchService.join()` 헬퍼가 `CompletionException`의 원인이
  `RuntimeException`이면 그대로 다시 던져서, 병렬화 이전과 동일한 예외 처리 경로(400/500 매핑)를 유지한다.

**효과**

전체 검색 지연시간이 "임베딩 + BM25 + kNN" 순차 합산에서 `max(BM25, 임베딩 + kNN)`으로 줄어든다.
세 호출이 비슷한 시간이 걸린다고 가정하면 이론상 약 1/3 수준으로 단축된다(실측은 운영 ES/Gemini API
응답시간에 따라 달라짐 - 별도 부하 테스트로 확인 필요).

**검증**

`JAVA_HOME`을 JDK 21로 두고(Gradle 자체 구동용) `./gradlew compileJava`로 컴파일 확인만 했다
(로컬에 ES/Gemini API 키가 준비된 환경에서의 end-to-end 재검증은 별도로 필요). 기존 RBAC 필터
로직(`buildBm25Body`/`buildKnnBody`), RRF 융합 공식(`fuseWithRrf`)은 변경하지 않았다.

**2026-09-10 실측 (`POST /api/search`, 동일 질의 15회 인터리브 측정)**

병렬화 이전 커밋(`0fe13f8`, 포트 8081)과 현재 코드(포트 8080)를 같은 Docker ES 인스턴스에 붙여
A/B로 비교했다(둘 다 동일 인덱스/데이터 조회, 요청을 번갈아 보내 시간대별 Gemini API 응답시간
드리프트가 한쪽에만 쏠리지 않게 함).

| | 순차 실행 (baseline, `0fe13f8`) | 병렬 실행 (현재) |
|---|---|---|
| 평균 | 1385ms | 1224ms (**-12%**) |
| 중앙값 | 1290ms | 1056ms (**-18%**) |

**위 "효과" 절의 "이론상 약 1/3 단축" 추정은 실측보다 낙관적이었다.** 이론치는 "세 호출(임베딩/BM25/
kNN)이 비슷한 시간이 걸린다"는 가정에 기반했는데, 실제로는 Gemini 임베딩 호출이 전체 지연시간의
대부분을 차지하고 BM25(ES 텍스트 매치)는 원래도 훨씬 빠르다. 병렬화로 없앨 수 있는 건 "BM25 대기
시간"뿐이라 전체 대비 개선폭이 이론치보다 작다. 개선 방향 자체는 유효하다(중앙값 기준 -18%).

**리스크/트레이드오프**

- 요청 하나당 검색 단계에서 가상 스레드 2개(BM25, 임베딩→kNN)를 추가로 쓴다. 가상 스레드는 OS
  스레드를 점유하지 않으므로 동시 요청이 늘어나도 스레드 고갈 문제는 없다.
- 두 결과 모두 `runSearch()`가 실패하면 첫 예외가 그대로 전파된다(기존과 동일하게 "부분 성공"은
  지원하지 않음 - RBAC 필터가 한쪽 쿼리에서만 빠지는 것을 방지하려면 두 쿼리 모두 성공해야 하므로
  의도된 동작).

## 2026-09-11: 답변 스트리밍(SSE)

**무엇을 바꿨나**

기존 `/api/chat`은 Gemini가 답변 전체를 다 생성한 뒤에야 응답이 왔다(체감 대기시간 = 전체 생성
시간). `RagChatService.askStream()` + `ChatController.chatStream()`(`POST /api/chat/stream`,
`text/event-stream`)을 추가해 `ChatClient.stream().content()`(`Flux<String>`)로 토큰이 생성되는
대로 SSE로 흘려보낸다. **기존 `/api/chat`은 그대로 남겨뒀다** - CLAUDE.md에 이미 문서화된 curl
예제가 계속 동작해야 하고(코딩 컨벤션: 요청 범위를 벗어난 변경 지양), 화면(`chat.js`)만 새 스트리밍
엔드포인트로 옮기면 충분하기 때문이다.

- 검색(ES 호출, 블로킹)은 `Schedulers.boundedElastic()`에서 실행해 서블릿 요청 스레드를 막지 않는다.
  citations(출처)는 검색이 끝나는 즉시 첫 SSE 이벤트("citations")로 먼저 보내고, 답변 토큰은 이어서
  "delta" 이벤트로 순서대로 내보낸다.
- **응답 상태 코드(200)가 스트림 시작 시점에 이미 커밋되므로, 검색/생성 중 오류가 나도
  `GlobalExceptionHandler`(400/500 매핑)가 더 이상 개입할 수 없다.** 그래서 `askStream()`이
  `onErrorResume`으로 모든 예외를 잡아 "error" SSE 이벤트로 스트림 안에서 알린다(연결이 끊기는 대신
  화면이 에러 문구를 렌더링할 수 있음). 검증(RBAC/ES 오류 등)에 따라 400/500을 구분하던 기존 정밀도는
  스트리밍 경로에서는 잃는다(트레이드오프로 감수).
- `EventSource`는 커스텀 헤더(CSRF 토큰)를 실어 POST할 수 없어서, `chat.js`는 `fetch()` +
  `ReadableStream`으로 직접 SSE 프레임(`\n\n`로 구분된 `event:`/`data:` 블록)을 파싱한다
  (`readSseEvents()`). 답변 텍스트는 델타가 올 때마다 누적해 `marked.parse()` + `DOMPurify.sanitize()`를
  다시 실행해 렌더링한다 - 매 delta마다 마크다운 재파싱은 하지만 청크 단위(문장 몇 개 수준)라 비용은
  무시할 만하다.

**효과**

전체 지연시간(서버가 답변을 다 만드는 시간)은 줄지 않지만, 사용자가 첫 텍스트를 보기까지의 시간이
"검색 + 전체 생성"에서 "검색 + 첫 토큰 생성"으로 줄어 체감 응답속도가 개선된다(백로그 표의 원래
목표와 동일 - 실제 처리량/지연시간 개선이 아니라 체감 개선 항목).

**검증**

`JAVA_HOME`을 JDK 21로 두고 `./gradlew compileJava`로 컴파일 확인 후, 로컬 Docker ES + 실제 Gemini
API 키로 앱을 띄워 브라우저(Chrome, USER 계정)로 end-to-end 확인했다: 질문 전송 → citations가 먼저
표시 → 답변이 마크다운으로 점진적으로 렌더링 → 문서에 없는 질문은 고정 문구 fallback도 정상 동작.
curl로 기존 `/api/chat`(비스트리밍)도 그대로 응답함을 재확인했다(하위 호환 유지 확인).

**2026-09-11 실측 (`/api/chat` vs `/api/chat/stream`, 동일 질의 인터리브 측정, USER 계정)**

Node.js로 두 엔드포인트를 번갈아 호출하는 벤치마크 스크립트를 작성해 측정했다. `/api/chat/stream`은
"첫 delta 이벤트 도착 시각"(=사용자가 답변 텍스트를 처음 보는 시점)과 "스트림 완료 시각"을 각각
쟀고, `/api/chat`은 (스트리밍 이전 방식과 동일하게) 응답이 오는 시각 하나만 있다.

| 질의(답변 분량) | N | `/api/chat` 총 응답(중앙값) | `/api/chat/stream` 첫 delta까지(중앙값) | 체감 개선 |
|---|---|---|---|---|
| "연차는 며칠인가요?" (~60자, 1~2문장) | 15 | 7669ms | 7510ms | **2.1%** |
| "연차 유급휴가 발생 기준과 사용 방법, 미사용시 처리에 대해 최대한 자세히 설명해줘" (~1000자) | 10 | 11685ms | 9366ms | **19.8%** |

**"효과" 절의 "체감 응답속도가 개선된다"는 주장은 답변 길이에 크게 의존한다는 게 실측으로 드러났다.**
짧은 한두 문장짜리 답변은 Gemini가 "생성을 시작하자마자 거의 다 끝나버려서" 스트리밍이 절약해주는
시간이 몇백 ms 수준(2.1%)에 불과하다. 반면 여러 문단의 긴 답변에서는 실제로 20% 가까이 체감
대기시간이 줄어든다(중앙값 기준 11685ms → 9366ms, 약 2.3초 단축). 사내 규정 Q&A 특성상 답변이
짧게 끝나는 질문(단답형 사실 조회)과 길게 설명이 필요한 질문(절차/기준 설명)이 섞여 있으므로,
스트리밍의 체감 효과는 "항상 크게 개선"이 아니라 "질문 유형에 비례해 개선"으로 이해해야 한다.
전체 완료 시간(스트림이 다 끝나는 시각)은 비스트리밍 대비 차이가 없었다(오히려 긴 질의 케이스에서
중앙값 기준 605ms 더 빨랐는데, 이는 개선이 아니라 두 엔드포인트를 인터리브로 호출할 때의 Gemini API
응답시간 변동 범위 안의 노이즈로 보인다) - 즉 스트리밍은 순수하게 "첫 텍스트가 보이는 시점"만
당겨줄 뿐 서버가 실제로 더 빨리 일하게 만드는 최적화는 아니다.

응답 하나를 델타 청크 단위로 직접 관찰해 진짜로 토큰 단위 점진 스트리밍이 되는지도 확인했다: 긴
답변 질의에서 23개의 "delta" SSE 이벤트가 약 1.6초에 걸쳐 순차적으로 도착함을 확인했다(모델이
전체를 다 만든 뒤 한 번에 밀어내는 게 아니라 실제로 점진적으로 옴). 반대로 위 짧은 답변 질의는
delta가 단 2개뿐이었는데, 이게 바로 짧은 답변에서 개선폭이 작은 이유다 - 스트리밍할 토큰 자체가
얼마 없기 때문이다.
